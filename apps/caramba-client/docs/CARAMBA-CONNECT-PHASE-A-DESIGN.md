# Phase A — Desktop native tunnel: design

**Date:** 2026-07-05
**Status:** Approved for implementation planning
**Author:** Caramba Connect native-client track

## 1. Context and verified current state

Caramba Connect adds a native cross-platform VPN client on top of the production
Caramba service. The Go engine (`libs/caramba-core`, mihomo/clash.meta behind
`-tags mihomo`) is wired to a Flutter client (`apps/caramba-client`) through the
`caramba_vpn` federated plugin and the `com.caramba/vpn` platform channels.

Verified on this machine (Go 1.26.4, CGO=1, macOS arm64) on 2026-07-05 — no
regression from the 2026-07-02 baseline:

| Check | Result |
| --- | --- |
| `go build ./...` (stub) | EXIT 0 |
| `go build -tags mihomo ./...` | EXIT 0 |
| `go vet -tags mihomo ./...` | EXIT 0 |
| `go test -tags mihomo ./...` | EXIT 0 (all packages pass) |

The desktop native bridge already exists and is **not a stub**. The Linux
C++/GObject plugin (`packages/caramba_vpn/linux/caramba_vpn_plugin.cc`) dlopens
`libcaramba_core.so`, resolves all 8 ABI symbols, drives `CarambaUp`/`CarambaDown`,
and polls status+traffic at ~1 Hz onto the EventChannels. The FFI loader, memory
ownership model, and channel contract are in place.

## 2. The problem: the brief's Phase A premise does not hold for macOS

The engineering brief states the desktop path is "just a CGO c-shared lib (no
NDK/Xcode/gomobile)" and recommends doing macOS first. That is true for **Linux
and Windows**, but **not macOS**. Per `INTEGRATION.md` (§ plugin table) and the
committed code:

| Platform | Coded tunnel path | cgo dylib? | Runnable on this Mac? |
| --- | --- | --- | --- |
| Linux / Windows | C++ dlopen `libcaramba_core.{so,dll}`, mihomo raises TUN in-process | Yes | No (cannot run a Linux/Windows GUI on macOS) |
| macOS / iOS | Swift **NetworkExtension** `PacketTunnelProvider`, separate process, App-Group IPC, links gomobile `exarobot.xcframework` | No (mobile path) | No (needs full Xcode + paid Apple dev account + System-Extension approval) |

macOS is effectively the mobile NetworkExtension path (Phase C territory). It
needs full Xcode (only CommandLineTools present), CocoaPods (absent), a gomobile
xcframework, Apple signing, and user approval in System Settings.

**Latent repo inconsistency to flag (not fix in Phase A):** `INTEGRATION.md`'s
vendoring step copies `libcaramba_core.dylib` to `macos/Libraries/`, but no macOS
code dlopens it — the macOS plugin is NetworkExtension-only. The dylib vendor line
for macOS is dead/aspirational.

### Environment constraints (this machine)

Missing: Flutter SDK, full Xcode, CocoaPods, the app runner scaffold
(`apps/caramba-client/{android,ios,macos,windows,linux}` — generated by
`flutter create .`, currently absent), and any live server to tunnel to. Present:
Go 1.26.4, clang, standalone `dart` 3.12.2.

## 3. Scope

Phase A is split into two independently valuable tracks that ARE achievable here,
plus an explicit handoff for what is not.

- **Track B — engine real tunnel** (the actual "first real end-to-end tunnel"):
  prove the mihomo core moves real packets on this Mac via the standalone CLI,
  decoupled from Flutter/Xcode.
- **Track A — desktop artifacts + bridge verification + Phase E stub demo**:
  build/vendor the cgo dylib, verify the full C-ABI and the native bridges, and
  demonstrate the Phase E stub false-positive. No server needed.
- **Out of scope (→ handoff runbook):** `flutter run -d macos` and any Flutter GUI
  run; the macOS NetworkExtension target; Phases B–E.

## 4. Track B — engine real tunnel (design)

### 4.1 Why the CLI, and the gap it has

The standalone CLI (`apps/caramba-cli`, its own Go module) is built with
`-tags mihomo` by `libs/caramba-core/scripts/build-desktop.sh`. On macOS, mihomo
(sing-tun) raises a `utun` device in-process — no Flutter, Xcode, or
NetworkExtension required, only root.

Gap: `api.Core.Up(ctx, serverID)` (`libs/caramba-core/api/api.go:528`) starts
mihomo's inbound listeners on background goroutines and **returns immediately**.
The existing `up` command prints success and exits, so the utun is torn down with
the process. `apps/caramba-cli/internal/cli/cmd_tunnel.go:9-14` documents exactly
this: end-to-end lifecycle needs a long-lived process (foreground or daemon).

### 4.2 The `--foreground` flag on `up` (approved approach)

Add a `--foreground` (`-f`) boolean flag to the existing `up` command. When set,
after `core.Up()` succeeds the command:

1. Installs a SIGINT/SIGTERM handler.
2. Enters a ~1 Hz poll loop: read `core.EngineStatus()` and `core.Traffic()`,
   print a compact status/traffic line (stage, active proxy, down/up bps + totals).
3. On signal, calls `core.Down()` (which invokes `executor.Shutdown()` → closes
   the TUN and restores routing), prints a teardown line, and exits 0.

Without `--foreground` the command keeps its current one-shot behavior (no
behavior change for existing users). The flag is additive.

**Unit boundary:** the poll-loop formatting (status+traffic → printable line) is a
pure function, unit-testable via TDD. The signal handling + `Down()` teardown are
covered by the live integration run (§4.4).

**Production safety:** `apps/caramba-cli` is a Connect-only, non-production Go
module. It is not in the panel/bot/sub/node runtime. Adding a flag cannot affect
the 20 production users.

### 4.3 Auth (panel + account path)

Per user decision, Track B uses the full `configure → connect` auth seam against a
real panel (default `https://exarobot.top`):

1. `caramba login --code <code>` (5-min code from the @exarobot Telegram bot) or
   `--email/--password`. Tokens persist to the on-disk token store.
2. `sudo caramba up --foreground [server]` reads the stored token, fetches the
   subscription, builds the mihomo config, and raises the utun.

Credentials are supplied by the user at execution time; they are not committed and
not written to the spec.

### 4.4 Live run and evidence

- Run under `sudo` on this Mac (mihomo creates the utun and installs routes). This
  temporarily reroutes this machine's traffic. Per user decision, the run happens
  here **if passwordless sudo is available**; otherwise the exact command is handed
  to the user. A concrete confirmation is required immediately before executing the
  rerouting step.
- **Evidence required to claim Track B done:**
  - Egress IP **changes** between pre-tunnel and post-tunnel `curl` (e.g.
    `curl -s https://ifconfig.me` or `api.ipify.org`), demonstrating packets exit
    via the node, not the local ISP.
  - `status` reports `connected` with a non-empty active proxy.
  - `Traffic()` counters (downTotal/upTotal) climb across successive polls.
  - Clean teardown on SIGINT restores the original egress IP / default route.

## 5. Track A — desktop artifacts, bridge verification, stub demo (design)

No server required; fully achievable on this machine.

### 5.1 Build and vendor the cgo dylib

- `cd libs/caramba-core && CGO_ENABLED=1 ./scripts/build-desktop-lib.sh` →
  `build/libcaramba_core.dylib` (+ generated header).
- Confirm all **10** C-ABI symbols are exported (`nm -gU build/libcaramba_core.dylib`
  filtered on `Caramba`): `CarambaNew`, `CarambaConfigure`,
  `CarambaImportSubscription`, `CarambaSetTunFd`, `CarambaUp`, `CarambaDown`,
  `CarambaStatus`, `CarambaTraffic`, `CarambaFree`, `CarambaFreeString`.
- Vendor per `INTEGRATION.md`. Note: the macOS dylib vendor target is dead (§2), so
  the primary vendored artifact that is actually consumed is the Linux `.so` (built
  on a Linux host) / Windows `.dll`. On this Mac we build and symbol-verify the
  `.dylib` as an ABI conformance check; it is not consumed by a runnable macOS
  plugin.

### 5.2 Runnable ABI proof (C harness)

A small C harness (in scratchpad, not shipped) that `dlopen`s the dylib and drives
`CarambaNew → CarambaStatus → CarambaTraffic → CarambaFree`, mirroring the
`caramba_core_ffi.h` dlopen/dlsym pattern the Linux/Windows plugin uses. Proves the
built artifact loads and the ABI binds and responds, at the exact boundary the
plugin depends on. (`CarambaUp` is not exercised here — it needs root + a server;
that is Track B's job.)

### 5.3 Parallel bridge audit (dynamic workflow)

A read-only audit workflow fanning out over the native bridges to confirm the
channel contract is honored end-to-end, so "bridges verified" is defensible:
Linux C++ (`caramba_vpn_plugin.cc`), Windows C++ (`caramba_vpn_plugin.cpp`),
macOS/darwin Swift (`CarambaVpnPlugin*.swift`, `PacketTunnelProvider.swift`,
`CarambaVpnShared.swift`), and the app consumer (`lib/vpn/vpn_service.dart`).
Each verifies: method names (`configure`/`connect`/`disconnect`), event maps
(`{stage, detail?, connectedSinceMs}` and `{downBps,upBps,downTotal,upTotal}`),
stage strings, and memory ownership (`CarambaFreeString` called exactly once per
returned string). Findings are reported; no code is changed in Phase A unless a
contract-breaking defect is found (which would be surfaced first).

### 5.4 Demonstrate the Phase E stub false-positive

Build the **stub** dylib (no `-tags mihomo`) and show, via the C harness, that
`CarambaUp` transitions to `connected` with zero traffic and no tunnel
(`engine_stub.go:39-42` sets `state = Connected` unconditionally). This is concrete
evidence motivating the Phase E fix (plumb `stub:true`/`HasNativeEngine()` so the
client hard-fails instead of showing a fake connection). Phase A only demonstrates
the bug; the fix is Phase E.

## 6. Verification bar (evidence before any "done" claim)

- **Track A:** dylib built; 10 ABI symbols present; C harness runs against the
  mihomo dylib (New/Status/Traffic/Free succeed); stub dylib demonstrates the
  false-positive; bridge audit returns green (or defects surfaced).
- **Track B:** CLI builds with `-tags mihomo`; `--foreground` poll-loop unit test
  passes; live run shows egress IP change + climbing counters + clean teardown.
- **CI/production:** no change to panel/bot/sub/node/mini-app runtime behavior.
  Any CLI change is verified with `go build -tags mihomo ./... && go test` in the
  `apps/caramba-cli` module and the workspace, and confirmed green on a real push
  before merge. `.github/workflows/ci.yml` must stay green.

## 7. Risks and mitigations

- **Passwordless sudo may be unavailable** → fall back to handing the user the
  exact sudo one-liner; they run it and paste the before/after egress IP.
- **No live server / bad creds** → Track B blocks at the live run; Track A and the
  CLI build + `--foreground` + stub demo still complete and are independently
  valuable. Egress proof deferred to the runbook.
- **Rerouting this Mac's traffic is invasive** → explicit confirmation immediately
  before the sudo run; `Down()`/Ctrl-C restores routing; verify egress IP returns
  to baseline after teardown.
- **mihomo bootstrap DNS / cold-start routing** (Phase E items) may affect a real
  RU-region run but not a generic egress-change test from this host; noted, not
  addressed in Phase A.

## 8. Out of scope (explicit)

- `flutter run -d macos` / any Flutter GUI run; macOS NetworkExtension target;
  `flutter create .` scaffold — captured in a handoff runbook instead.
- Phase B (flutter analyze re-gating), Phase C (gomobile mobile bindings),
  Phase D (licensing/enrollment/migrations), Phase E (security fixes). Each is a
  separate spec → plan → implementation cycle.
